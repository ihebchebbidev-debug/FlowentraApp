## Goal

Allow users to create a Service Order directly — without first going through Offer or Sale — while preserving today's downstream flow (billing, accounting, reporting) by auto-generating a "shadow" Sale at completion time.

## UX

### Entry points
1. **Service Orders list page** — primary `+ New Service Order` button (top right, next to existing filters).
2. **Global create menu** — add `Service Order` as a new item alongside Offer / Sale / Invoice.

Both routes open the same `DirectServiceOrderCreate` dialog/page.

### Create form (single screen, progressive)
Minimum to save = **Customer only** → order is created with status `Draft`.

Sections, top to bottom:
1. Customer (contact picker, required) — searchable, with "Create new contact" inline.
2. Optional context — project, site/address (auto-filled from contact, editable), reference / PO number, internal notes.
3. Lines — catalog-driven picker (services + articles), unit price auto-filled from current price list for that customer, editable per line (qty, unit price, discount, VAT). "Add custom line" allowed.
4. Scheduling — date, time window, assigned technician/team. All optional at create.
5. Footer — totals (live), `Save as Draft`, `Save & Schedule` (only enabled if at least one line + date are set).

Behavior:
- Save with customer only → status `Draft`, no lines, no shadow Sale yet.
- User can return later to add lines, schedule, dispatch.
- Order cannot move past `Scheduled` until it has ≥1 line.

### Status lifecycle
`Draft` → `Scheduled` → `In Progress` → `Completed` → `Invoiced` → `Closed`
(plus `Cancelled` from any pre-Completed state)

`Completed` is the trigger for shadow Sale generation.

## Data model

Reuse existing `ServiceOrder` table. Changes:

- `OfferId` — already nullable, keep.
- `SaleId` — make nullable (currently likely required).
- Add `Origin` enum column: `FromOffer | FromSale | Direct` (default existing rows to `FromSale`).
- Add `AutoGeneratedSaleId` (nullable FK to Sale) — populated when the shadow Sale is created at completion.

`Sale` table:
- Add `IsAutoGenerated` boolean (default false).
- Add `SourceServiceOrderId` (nullable FK back to ServiceOrder).

These two flags drive the "tagged as auto-generated" UI in the Sales module — a chip `Auto from SO-00123` on the row, with a link back to the order.

Numbering: same sequence as existing service orders. No prefix change.

Permissions: same permission as today (`ServiceOrder.Create`). No new role.

Multi-tenancy: `ServiceOrder` already carries `TenantId` via Layer 2; new rows stamped automatically by `SaveChangesAsync`. Shadow Sale inherits the same `TenantId` from the order — explicit set in the generator, not relying on ambient context, to be safe under `X-Target-Tenant`.

## Backend

### New endpoints
- `POST /api/service-orders/direct` — body: `{ contactId, projectId?, siteAddress?, reference?, notes?, lines?: [...], schedule?: {...} }`. Creates order in `Draft` (or `Scheduled` if lines + date provided). Returns the created order.
- `PATCH /api/service-orders/{id}` — already exists; ensure it accepts adding lines / schedule to a Direct/Draft order.
- `POST /api/service-orders/{id}/complete` — existing or new. On success, if `Origin == Direct` and `AutoGeneratedSaleId is null`, run **ShadowSaleGenerator**.

### ShadowSaleGenerator (new service)
Pure function over the order:
1. Build a `Sale` with `IsAutoGenerated = true`, `SourceServiceOrderId = order.Id`, customer/lines/totals copied from the order, same `TenantId`.
2. Persist inside the same transaction as `order.Status = Completed`.
3. Set `order.AutoGeneratedSaleId = sale.Id` and `order.SaleId = sale.Id` (so downstream code that reads `SaleId` keeps working unchanged).
4. Hand off to the existing invoice-from-sale flow per current rules (auto or manual depending on tenant settings).

Idempotency: completion endpoint is a no-op if `AutoGeneratedSaleId` already set. Guards against double-clicks and replayed offline mutations.

### Validation
- Customer must exist and belong to current tenant.
- Catalog items resolved server-side; client-sent prices accepted only within an allowed override range (reuse existing offer/sale line validation).
- Cannot complete an order with zero lines.

## Sales module changes
- List: new column / chip `Auto-generated` (filter included by default, hideable via filter).
- Detail: banner `Generated from Service Order SO-00123` linking back.
- Edit restrictions: auto-generated sales are read-only for lines (source of truth is the order); only payment / invoice metadata editable.

## Offline behavior
Direct create works offline like other mutations — queued, labeled with the customer name and `Service order (draft)` so users can identify pending items. Completion (and therefore shadow Sale creation) requires online to avoid duplicate Sale numbering.

## Migration
1. EF migration: `ServiceOrder.SaleId` nullable, add `Origin`, `AutoGeneratedSaleId`; `Sale.IsAutoGenerated`, `SourceServiceOrderId`.
2. Backfill: all existing orders → `Origin = FromSale`.
3. Deploy backend → deploy frontend.

## Out of scope (call out explicitly)
- Recurring service orders.
- Non-billable / internal orders (could be a follow-up by adding a `Billable` flag — currently every direct order will produce a shadow Sale on completion).
- New permission role.
- Distinct numbering prefix.

## Open follow-ups (will assume defaults unless you object)
- Tax / VAT defaults on lines: use customer's default VAT, same as Sales today.
- Currency: customer's default currency, not selectable on the form.
- If customer has no price list, fall back to catalog list price.
